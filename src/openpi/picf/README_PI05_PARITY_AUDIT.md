## 2. Reference PI0.5 Contract

The reference PI0.5 CALVIN training path is not only the action-flow loss. The
contract is:

```text
raw CALVIN frame
-> repack transforms
-> data transforms
-> Normalize(norm_stats)
-> TokenizePrompt(prompt, normalized live state)
-> PadStatesAndActions(action_dim=32)
-> preprocess_observation_pytorch(train=True)
-> Pi0Pytorch.forward(...)
-> MSE(noise - normalized_action_chunk, predicted_velocity)
```

For `pi05_calvin_nosonata`:

- `enable_sonata=False`
- `max_token_len=200`
- `action_horizon=16`
- `action_dim=32`
- no point cloud is present
- `preprocess_observation_pytorch(..., train=True)` enables image augmentation
  because the observation has no point cloud

For `pi05_calvin_sonata`:

- `enable_sonata=True`
- `max_token_len=200`
- `action_horizon=16`
- `action_dim=32`
- point clouds are constructed from CALVIN depth/RGB
- image augmentation is disabled by the point-cloud guard, because random RGB
  geometry without matching point/depth transforms would break alignment

The flow objective is:

```text
t ~ Beta(1.5, 1.0) * 0.999 + 0.001
x_t = t * noise + (1 - t) * action_target
u_t = noise - action_target
loss = MSE(u_t, v_theta(prefix, suffix(x_t, t)))
```

## 3. Current PICF Enabled Contract

The full PICF mode is intentionally not a byte-identical PI0.5 replica. Its
contract is:

```text
raw CALVIN window
-> PicfObservation frames
-> PaliGemma semantic encode
-> PICF physical observe_step
-> task readout over public_read_memory=[fused_tokens, visual_tokens]
-> canonical conditioned control state C_t
-> PI0.5 flow loss with extra_prefix_tokens=C_t^pi
-> finalize_with_action(...)
-> physical predictive basis K_t^phys
-> conditioned future cache K_t^cond
```

The hard boundaries remain:

- semantic does not enter physical observation-anchor construction
- semantic does not enter posterior update
- innovation reads only the previous physical prediction cache
- final action is generated by the PI0.5 flow/action path
- `C_t` is the single canonical conditioned control state

The current canonical full PICF training profile keeps:

- `picf_mode=enabled`
- `unroll_steps=2`
- `action_horizon=16`
- `save_interval=2500` for current cloud long runs
- prompt-state normalization inherited from the same CALVIN norm stats used for
  action normalization
- Sonata/V-JEPA/AnyTouch/PaliGemma enabled according to the selected foundation
  profile

## 4. Current PI0.5-Only Ablation Contract

The ablation mode disables the PICF physical/control/future branches while
keeping the same trainer and PaliGemma action generator family:

```text
raw CALVIN window
-> PicfObservation frames
-> PaliGemma semantic encode
-> PI0.5 flow loss with extra_prefix_tokens=None
```

In code:

- `PicfPi05Policy(picf_enabled=False)` calls
  `semantic_encoder.compute_action_flow_loss(..., extra_prefix_tokens=None)`
- no `observe_step(...)` or `finalize_with_action(...)` is used
- no recurrent PICF state is returned
- unused PICF core parameters are frozen in the ablated profile

This is the correct ablation for measuring the contribution of PICF inside the
current trainer/runtime family. It is not automatically strict no-Sonata PI0.5
parity unless the parity knobs below are also set.

## 5. Confirmed Matching Pieces

These pieces match the reference PI0.5 action-flow family closely enough for
action-loss comparison when normalization and sampling context are aligned:

- action horizon is restored to `16`
- action dim is `32`
- action targets are normalized before flow loss
- prompt-state tokenization now uses normalized live CALVIN state and does not
  pad state to `32` before tokenization
- time sampling uses the same `Beta(1.5, 1.0) * 0.999 + 0.001` family
- flow target is `noise - target`
- noisy action is `t * noise + (1 - t) * target`
- predicted velocity is produced by the PaliGemma/action-expert path and
  `action_out_proj`
- inference denoising uses the same Euler-style update family with default
  `denoise_steps=10`

The action loss fields are therefore semantically comparable:

- `loss_action`
- `loss_action_pos`
- `loss_action_rot`
- `loss_action_gripper`
- `loss_action_active7`

They are still not strictly identical across runs unless norm stats, data
sampling, model width, augmentation, and optimizer history are also aligned.

## 6. Real Differences That Matter

### 6.1 Image preprocessing

Reference no-Sonata PI0.5 training uses
`preprocess_observation_pytorch(..., train=True)`, and because no point cloud is
present, train-time image augmentation is active.

Current PICF wrapper image preparation is manual:

```text
HWC RGB
-> range normalize
-> clamp
-> [-1, 1]
-> resize_with_pad_torch(224, 224)
-> BCHW
```

The maintained full-PICF default does not apply the reference no-point-cloud RGB
train augmentation.

This difference can explain the observed pattern where a run has low training
loss but weaker chained CALVIN rollout robustness. It makes the train
distribution easier but can reduce robustness after the first task changes the
scene.

For full PICF, blindly enabling RGB-only geometric augmentation is not safe
because depth/point geometry must remain aligned. For strict no-Sonata ablation
parity, matching no-Sonata augmentation is a valid future option.

Current implementation status:

- `--picf-augmentation-mode off` is the default and preserves the maintained
  full-PICF contract.
- `--picf-augmentation-mode photometric` applies geometry-preserving
  brightness/contrast/saturation jitter to RGB inputs before point construction.
  This is safe for full PICF because it does not crop, rotate, warp, or move
  pixels relative to depth/camera geometry.
- `--picf-augmentation-mode multimodal_geometry` is reserved and intentionally
  fail-fast. It must not be enabled until RGB, depth, point coordinates, and
  camera intrinsics/extrinsics are transformed together.
- The exact reference no-Sonata crop/rotation augmentation is still not a full
  PICF default and should only be used in a dedicated no-point-cloud parity
  profile.

### 6.2 Norm stats path

Current PICF defaults to:

```text
assets/pi05_calvin_sonata/calvin/norm_stats.json
```

This is the correct default for maintained full PICF + Sonata-style runs. It is
not strict no-Sonata parity if the comparison baseline uses a different
no-Sonata checkpoint asset tree.

If the purpose is strict no-Sonata parity, pass:

```text
--action-norm-stats-path <nosonata norm_stats.json>
--prompt-state-norm-stats-path <same nosonata norm_stats.json>
```

If the purpose is full PICF training, keep the full-PICF/Sonata stats consistent
between training and serving.

### 6.3 Optimizer-state continuity in ablation

With `optimizer_checkpoint_mode=auto`, ablated checkpoints default to model-only
semantic checkpoints. This is intentional because full semantic optimizer state
is very large.

For long interrupted ablation curves, this means Adam moments reset across
resume unless `--optimizer-checkpoint-mode full` is used. That makes a resumed
ablation curve operationally different from an uninterrupted reference run.

Full PICF enabled mode in `auto` saves optimizer state unless the optimizer
sharding mode prevents it.

### 6.4 Max token length

Reference CALVIN PI0.5 configs use `max_token_len=200`.

Current PaliGemma semantic config default is `max_length=256`.

This is usually low risk when valid prompt/state tokens fit under 200 because
extra positions are masked padding. For strict parity testing, set the semantic
max length to `200`.

The current CLI can set this explicitly via `--semantic-max-length 200`. The
maintained long-run full-PICF profile may keep a larger prompt budget, but any
strict PI0.5 parity claim must state the prompt budget used.

### 6.5 Frozen perception profile

The current code also supports a resource-aware frozen-perception profile:

```text
--perception-finetune-mode frozen
--visual-feature-mode hierarchical
```

This freezes Sonata, V-JEPA, and AnyTouch-style perception backbones while
keeping their feature interfaces available to PICF. It is a valid training
regime when comparing frozen-perception PICF variants, but it is not full
all-backbone cotraining and should not be presented as such.

The `visual_feature_mode=hierarchical` option exists because frozen V-JEPA must
not silently change its feature contract from hierarchical patch evidence to a
single final-layer feature path. This is a capacity-preserving interface choice,
not a new model objective.

## 7. False Positives Rejected

These were checked and should not be used as primary root-cause claims without
new evidence:

- EMA mismatch: PyTorch reference training logs that EMA is not supported, so
  lack of EMA in PICF PyTorch ablation is not a high-confidence issue.
- Flow-loss formula mismatch: current wrapper and reference PI0.5 share the
  same noise/time/noisy-action/velocity-MSE family.
- Action chunk buffering as an ablation-vs-PICF differential in the current
  CALVIN wrapper: `scripts/calvin/evaluate_picf_policy.py` consumes `actions[0]`
  from the served checkpoint in the same way for PICF-enabled and ablated
  checkpoints.
- Missing masked right-wrist placeholder as a primary explanation: masked image
  slots do not increase effective position IDs; it can matter for exact
  byte-level parity but is not enough to explain rollout collapse by itself.

## 8. Recommended Comparison Protocols

### 8.1 Full PICF quality run

Use this when evaluating whether the v2.2 architecture helps:

- `picf_mode=enabled`
- `unroll_steps=2`
- `action_horizon=16`
- full multimodal foundation profile as selected
- full-PICF/Sonata-compatible norm stats
- save checkpoints every `2500` steps for current cloud runs
- run CALVIN video evaluation through `scripts/serve_picf_policy.py` and
  `scripts/calvin/evaluate_picf_policy.py`

This is the main system, not a PI0.5 parity replica.

### 8.2 Maintained PI0.5-only ablation

Use this when asking whether PICF additions help within the current trainer:

- `picf_mode=ablated`
- `unroll_steps=2` if comparing against the current v2.2 window trainer
- `action_horizon=16`
- `extra_prefix_tokens=None`
- same norm stats as the target training family

This is the maintained ablation. It is allowed to differ from historical
no-Sonata PI0.5 in trainer/runtime details.

### 8.3 Strict no-Sonata PI0.5 parity ablation

Use this only when the goal is exact reference no-Sonata parity:

- `picf_mode=ablated`
- no-Sonata norm stats for both action and prompt state
- `unroll_steps=1`
- `semantic_max_length=200`
- reference-style no-point-cloud train image augmentation
- optimizer checkpoint mode set to `full` if the run will be interrupted and
  resumed

This mode is stricter than the maintained ablation and should be documented as a
parity probe, not the main v2.2 training definition.

## 9. CALVIN Result Interpretation

CALVIN reports chained success:

- `1/5`: first task in the chain succeeds
- `2/5`: first two tasks succeed
- `5/5`: all five tasks succeed

The pattern "strong 1/5 but weak 2/5+" means the policy can start tasks from a
reset-like state but is weaker after its own actions alter the scene. This is
more consistent with rollout robustness / train-eval contract differences than
with a simple action-loss-formula bug.

Therefore:

- do not judge quality from `loss_action` alone
- compare `loss_action_pos`, `loss_action_rot`, and `loss_action_gripper`
  separately
- validate with CALVIN video rollouts at representative checkpoints
- keep training/eval norm stats identical for a given experiment

## 10. Current Audit Verdict

The current PICF code matches the v2.2 architecture contract:

- physical core remains world-only
- task readout is current-step and semantic-conditioned
- `C_t` is the canonical conditioned control state
- final action generation is PI0.5 flow/sampler
- full PICF serving uses the sampled action to finalize physical future state

The PI0.5-only ablation is implemented and useful, but it should be described
precisely:

- it is an ablation of PICF branches inside the v2.2 trainer/runtime
- it is not automatically a byte-identical no-Sonata PI0.5 reproduction
- strict reference parity requires explicit norm, token length, augmentation,
  unroll, and optimizer-history settings

No current code evidence supports a claim that the action-flow loss itself is
mathematically wrong. The remaining quality differences are best explained by
runtime/training-contract differences and rollout robustness, not by a broken
PI0.5 action objective.

## 10.1 Bug Ledger

This is the current high-level classification of PI0.5/PICF differences.

### Fixed real bugs

These were real contract bugs or implementation mistakes and are now fixed in
the current code path:

- `action_horizon` is restored to `16`, matching the CALVIN PI0.5 chunk
  contract.
- Prompt-state tokenization now normalizes live CALVIN state with the same
  `norm_stats.json` family used by action normalization before discretizing it
  into prompt tokens.
- Prompt-state tokenization no longer pads state to `action_dim = 32` before
  tokenization. Padding remains a later state/action tensor contract.
- `_CalvinTransitionSource` samples language segments first, then valid starts
  inside the selected segment. This avoids the earlier window-start weighting
  bug.
- `picf_mode=ablated` now explicitly disables PICF recurrent/control/future
  branches and calls the PI0.5 action path with `extra_prefix_tokens=None`.
- `picf_mode=enabled` uses PI0.5 flow matching / sampler as the final action
  path and finalizes physical future only after the teacher or sampled executed
  action is known.
- Unsafe multimodal geometric augmentation is fail-fast rather than silently
  applying image-only geometry to a geometry-coupled PICF sample.

### Acceptable intended differences

These are not bugs when the goal is full v2.2 PICF training:

- Full PICF adds `W_t`, task readout `R_t`, canonical conditioned control state
  `C_t`, PI0.5 extra-prefix view `C_t^pi`, `K_t^{phys}`, and `K_t^{cond}`.
- Full PICF uses `public_read_memory=[fused_tokens, visual_tokens]`, preserving
  the fused point/tactile/context memory while adding visual tokens that are not
  included in `fused_tokens`.
- Full PICF uses `unroll_steps=2` in the maintained window trainer so that
  recurrent state and future supervision are exercised. This is not byte-level
  PI0.5 training parity, but it is the intended PICF training shape.
- Full PICF uses a Sonata/full-PICF-compatible norm-stats path when training and
  serving the Sonata-backed system. This is correct if the same stats are used
  consistently end to end.
- Full PICF keeps RGB geometry augmentation off by default because RGB, depth,
  point coordinates, and camera geometry must stay aligned.
- Frozen-perception training is an explicit profile, not a hidden default. It is
  acceptable only when the experiment is labeled as frozen-perception PICF.
- FSDP/trainer-shell differences are acceptable operational differences when
  comparing within the same current trainer family. They are not strict
  main-branch PI0.5 parity.

### Open strict-parity gaps, not full-PICF bugs

These still matter when the goal is strict PI0.5/no-Sonata reproduction, but
they are not bugs in the maintained full PICF contract:

- Strict no-Sonata parity still requires the no-Sonata checkpoint's own
  `norm_stats.json` for both action and prompt-state normalization.
- Strict no-Sonata parity should use `--semantic-max-length 200`.
- Strict no-Sonata parity should use `unroll_steps=1` unless the comparison is
  explicitly between window-trainer variants.
- Strict no-Sonata parity should match the no-point-cloud image augmentation
  policy. Current full PICF intentionally does not enable reference crop/rotate
  geometry by default.
- Strict interrupted ablation parity should use
  `--optimizer-checkpoint-mode full`; otherwise Adam moments reset across
  resume.
- Strict `pi0.5_sonata` parity is not achieved by `picf_mode=ablated`, because
  ablated mode intentionally removes PICF/Sonata/V-JEPA/AnyTouch branches. Use
  it as a PI0.5-only ablation inside the PICF trainer, not as a byte-identical
  historical Sonata replica.

### No high-confidence open code bug

As of this audit, there is no code-level evidence that the following are still
broken:

- action flow formula
- PI0.5 sampler update rule
- action target normalization for maintained full-PICF runs
- prompt-state normalization when a normalizer path is configured
- semantic leakage into physical posterior or innovation
- reintroduction of dual canonical control states

The remaining actionable work is experiment-definition clarity and optional
strict-parity profiling, not a known mathematical bug in the PICF/PI0.5 action
path.

## 11. File-By-File Follow-Through

This section records the local follow-through used for the latest audit. It is
intentionally file-oriented so that future comparisons can distinguish real
training-contract differences from false positives.

### 11.1 Reference PI0.5 / no-Sonata / Sonata files

`src/openpi/training/config.py`

- Defines `pi05_calvin_nosonata` and `pi05_calvin_sonata`.
- Both use `Pi0Config(pi05=True, discrete_state_input=True)`.
- Both current CALVIN reference configs use:
  - `max_token_len=200`
  - `action_horizon=16`
  - `action_dim=32`
- `pi05_calvin_nosonata` has `enable_sonata=False` and uses
  `CalvinNoSonataDataConfig`.
- `pi05_calvin_sonata` has `enable_sonata=True` and uses `CalvinDataConfig`
  with depth-to-point-cloud construction.
- The model transform order is:
  - `ResizeImages(224, 224)`
  - `TokenizePrompt(..., discrete_state_input=True)`
  - `PadStatesAndActions(action_dim=32)`

`src/openpi/training/data_loader.py`

- Applies dataset transforms in the reference order:
  - repack transforms
  - data transforms
  - `Normalize(norm_stats, use_quantiles=True)` for PI0.5
  - model transforms
- This means reference prompt-state tokenization sees normalized live state, not
  raw `robot_obs`.

`src/openpi/transforms/_base.py`

- `Normalize` owns the reference state/action normalization contract.
- `TokenizePrompt` owns prompt and discrete-state tokenization.
- `PadStatesAndActions` pads state and actions only after prompt tokenization.
- Therefore state padding to `32` is not part of the text prompt string.

`src/openpi/models_pytorch/preprocessing_pytorch.py`

- Owns the reference image preprocessing path.
- In the reference no-Sonata training path, `train=True` and no point cloud is
  present, so RGB train-time augmentation is active.
- In the reference Sonata path, a point cloud is present, so RGB-only geometric
  augmentation is guarded off to avoid breaking image/depth/point alignment.
- This file is the strongest reference for judging whether a PICF ablation is
  strict no-Sonata parity or merely action-objective parity.

`src/openpi/models_pytorch/pi0_pytorch.py`

- Owns the reference PyTorch PI0.5 action-flow objective:
  - sample `noise`
  - sample `time`
  - build `x_t = t * noise + (1 - t) * action_target`
  - build `u_t = noise - action_target`
  - predict `v_t` from prefix and suffix transformer states
  - optimize MSE between `u_t` and `v_t`
- Owns the reference sampler:
  - build prefix cache
  - start from Gaussian noise
  - run Euler denoising
  - output a full normalized action chunk

`scripts/train_pytorch.py`

- Owns the reference PyTorch training loop.
- The PyTorch reference path logs that EMA is not supported, so EMA mismatch is
  not a valid high-confidence explanation when comparing against the current
  PyTorch no-Sonata / Sonata baselines.

### 11.2 Current PICF files

`scripts/picf_core_train.py`

- Owns runtime argument normalization, checkpointing, window sampling, and the
  training loop.
- `_CalvinTransitionSource` constructs a CALVIN window and emits:

  - normalized `action`
  - normalized `action_chunk`

- In `picf_mode=ablated`, unused PICF core parameters are frozen.
- In `optimizer_checkpoint_mode=auto`, ablated checkpoints are model-only by
  default; use `full` if optimizer-state continuity matters for a resumed

`src/openpi/picf/action_normalization.py`

- Owns the PICF action/state normalizer used by the trainer and serving path.
- The default norm-stats path is the maintained full-PICF/Sonata-style CALVIN
  path.
- That default is correct for full PICF runs, but strict no-Sonata parity must
  explicitly pass the no-Sonata checkpoint's own `assets/calvin/norm_stats.json`
  for both action and prompt-state normalization.

`src/openpi/picf/paligemma/config.py`

- Owns current PaliGemma wrapper defaults:
  - `action_horizon=16`
  - `action_dim=32`
  - `denoise_steps=10`
  - `inject_state_into_prompt=True`
  - `prompt_state_normalization` configurable
- The wrapper default `max_length=256` is not strict reference parity against
  CALVIN PI0.5's `max_token_len=200`, although the extra positions are usually
  masked padding when prompts fit under 200.

`src/openpi/picf/paligemma/wrapper.py`

- Owns PICF's PaliGemma semantic/action path.
- `_prepare_image(...)` performs range normalization, resize-with-pad, and BCHW
  conversion.
- `_prepare_image(...)` does not apply the reference no-Sonata train-time RGB
  augmentation.
- `_state_for_prompt(...)` now normalizes live state before prompt tokenization
  when a prompt-state normalizer is configured.
- `_state_for_prompt(...)` does not pad to `action_dim=32` before tokenization,
  matching reference transform order.
- `compute_action_flow_loss(...)` matches the PI0.5 flow-loss family.
- `sample_action_chunk(...)` returns a full normalized action chunk.

`src/openpi/picf/policy.py`

- Owns the exported policy-level contract.
- Enabled mode:
  - encodes semantic features
  - runs `core.observe_step(...)`
  - feeds `conditioned_control.pi_prefix_tokens` into PI0.5 action flow
  - finalizes PICF future with the teacher/sampled action
- Ablated mode:
  - encodes semantic features
  - calls PI0.5 flow/sampler with `extra_prefix_tokens=None`
  - returns no PICF recurrent state
- This is the correct ablation of PICF branches inside the v2.2 runtime, but it
  is not automatically strict no-Sonata PI0.5 parity.

`src/openpi/picf/core/pipeline.py`

- Owns the full PICF physical and conditioned-control path.
- Physical core remains:
  - observation-anchor construction
  - posterior update
  - world-only innovation
- Semantic enters:
  - task query conditioning
  - current-step task readout
  - conditioned control state `C_t`
  - PI0.5 native semantic/action stream
- Semantic does not enter:
  - observation-anchor construction
  - posterior update
  - next-step innovation base
- `public_read_memory=[fused_tokens, visual_tokens]` preserves fused
  point/tactile/context public tokens while adding visual tokens that are not
  inside `fused_tokens`.
- `finalize_with_action(...)` builds the physical predictive basis only after
  the teacher/sampled executed action is known.

`scripts/serve_picf_policy.py`

- Owns checkpoint loading and websocket serving for enabled and ablated modes.
- Loads checkpoint metadata and runtime args before model construction.
- Reconstructs the action normalizer and unnormalizes the first action before
  returning it to CALVIN.
- `--picf-mode enabled` and `--picf-mode ablated` are explicit serving modes;
  if omitted, mode is inferred from checkpoint metadata.

`scripts/calvin/evaluate_picf_policy.py`

- Owns current CALVIN rollout evaluation for PICF checkpoints.
- Sends observation image, wrist image, depth, state, prompt, and reset metadata
  over websocket.
- Consumes `actions[0]` from the server output.
- This first-action consumption is shared by enabled and ablated checkpoints
  served through this evaluator, so it is not a differential explanation between
  those two modes.

## 12. Root-Cause Classification

The current local audit separates findings into three groups.

### 12.1 High-confidence real differences

- Strict no-Sonata parity requires reference no-point-cloud RGB augmentation;
  current PICF wrapper does not apply it.
- Strict no-Sonata parity requires no-Sonata norm stats for both action and
  prompt state; the maintained full-PICF default is Sonata/full-PICF stats.
- Strict resumed ablation parity requires optimizer-state continuity; model-only
  ablated checkpoints do not preserve Adam moments.
- Strict no-Sonata parity uses `max_token_len=200`; current wrapper default is
  `256`.

### 12.2 Intended full-PICF differences

- Full PICF adds physical posterior, task readout, canonical `C_t`, PI0.5
  extra-prefix conditioning, physical future prediction, and conditioned future
  prediction.
- Full PICF should use a geometry-consistent preprocessing contract. Do not
  blindly copy no-Sonata RGB geometric augmentation into full PICF unless
  corresponding depth/point transforms are also applied.

### 12.3 Rejected false positives

- EMA mismatch is not a high-confidence PyTorch PI0.5 comparison issue because
  the reference PyTorch trainer does not support EMA.
- The action flow formula is not currently wrong; PICF wrapper and reference
  PI0.5 use the same `x_t`, `u_t`, and velocity-MSE family.
- Missing fully masked right-wrist image slots may matter for byte-level parity,
  but masked tokens do not advance effective position IDs and are not enough by
  themselves to explain chained rollout collapse.
- Chunk buffering is not a PICF-enabled-vs-ablated differential under the
  current evaluator because both consume `actions[0]`.

## 13. Practical Interpretation

Use three different labels, not one:

- **Full PICF quality run**:
  evaluate whether v2.2 PICF improves behavior. This should use the full
  multimodal PICF contract and its matching norm/preprocessing choices.
- **Maintained PI0.5-only ablation**:
  evaluate whether disabling PICF branches inside the current trainer/runtime
  changes behavior. This is the main ablation for the v2.2 codebase.
- **Strict no-Sonata parity probe**:
  evaluate whether the PICF trainer can reproduce the historical no-Sonata
  PI0.5 contract. This requires explicit parity knobs and should not be confused
  with the maintained ablation.

When reading CALVIN results:

- `1/5` mostly measures first-task start competence.
- `2/5+` measures continuation after the policy has changed the scene.
- A lower training action loss can coexist with weaker `2/5+` if preprocessing,
  normalization, or optimizer-history contracts differ.
- For action-loss comparison, `loss_action`, `loss_action_pos`,
  `loss_action_rot`, and `loss_action_gripper` are mathematically comparable
  only after normalization, horizon, and sampling context are aligned.
